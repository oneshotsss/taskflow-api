## AI Output Audit: Top 3 реальних проблем, які AI допустив (Лабораторна 2)

### 1. `deleteProject` без транзакції — прямо суперечило spec

- **Що AI зробив**: у коміті `4f44621` AI написав `deleteProject`, який робив три окремі запити на пулі (SELECT → DELETE tasks → DELETE project) без `BEGIN`/`COMMIT`. Spec Scenario 4 прямо каже «within a transaction».
- **Як помітив**: запустив сценарій на реальній БД, подивився логи — немає `BEGIN`/`COMMIT` при видаленні. Перечитав spec і побачив невідповідність.
- **Як виправлено**: переписав `deleteWithTasks` на `withTransaction`, прибрав зайвий SELECT, «not found» визначається через `rowCount` (коміт `0e93a53`).

### 2. FK-violation давав 500 замість 400

- **Що AI зробив**: AI не додав маппінг PostgreSQL SQLSTATE помилок на HTTP-коди. `POST /projects { "userId": 1 }` на свіжій БД (таблиця `users` порожня) падав з 500 — SQLSTATE `23503` не перехоплювався.
- **Як помітив**: запустив приклад з spec.md (`"userId": 1`) на чистій БД — отримав 500 Internal Server Error замість 400.
- **Як виправлено**: додав `translatePgError` у `src/db/query.js` — `23503` → `ValidationError(400)`, `23505` → `ConflictError(409)` (коміт `bd381f2`).

### 3. Нечисловий `:id` і невалідні поля тіла давали 500

- **Що AI зробив**: валідація `:id` не існувала — `GET /projects/abc` йшов прямо у SQL, PostgreSQL кидав `22P02`, error handler повертав 500. Те ж із `userId: "abc"`, `initialTasks: "string"`, name > 255 символів.
- **Як помітив**: протестував вручну `GET /projects/abc` і `POST /projects { "userId": "abc" }` — обидва повернули 500.
- **Як виправлено**: додав `parseId`, `parseOptionalRef`, `requireText` у service-шарі до будь-якого звернення до репозиторію (коміт `1daa949`).

Також AI дозволив перехід `IN_PROGRESS → TODO`, якого немає в spec — виправлено в `925b9fe`.
