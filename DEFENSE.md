# DEFENSE.md — Лабораторна робота 2

## 1. Що і навіщо (1-2 речення)

Реалізовано 4 ключові бізнес-сценарії Taskflow API (транзакційне створення проєктів із задачами, вибірка без N+1, життєвий цикл статусів, каскадне видалення) спершу на статичних in-memory даних, а потім із повноцінною інтеграцією PostgreSQL, пулом з'єднань, транзакціями та ізоляцією шарів. Для усунення протягування параметрів (`processId`, `userId`) використано `AsyncLocalStorage`, а всі помилки централізовано обробляються єдиним глобальним middleware.

## 3. Ключові рішення — альтернативи й чому обрав

- **Вибір БД та робота з даними** (деталі: `docs/adr/0003-database-and-sql-repository.md`):
  - _Альтернативи_: Prisma / TypeORM, SQLite (`better-sqlite3`), MongoDB.
  - _Чому обрано_: PostgreSQL через драйвер `pg` з пулом з'єднань на ізольованому порті `5439` (у `docker-compose.yml`) та сирим SQL у репозиторіях (`PostgresProjectRepository`, `PostgresTaskRepository`). Це забезпечує повний контроль над запитами, унеможливлює приховані N+1 запити ORM і суворо відокремлює шар доступу до даних від бізнес-сервісів та HTTP-роутів.
- **Керування залежностями та Process ID** (деталі: `docs/adr/0004-context-and-dependency-management.md`):
  - _Альтернативи_: прокидання 10–15 параметрів через усі функції (parameter drilling), важкі сторонні DI-фреймворки (InversifyJS).
  - _Чому обрано_: нативний `AsyncLocalStorage` (`node:async_hooks`). Контекст (`processId`, `userId`) автоматично створюється в `contextMiddleware` і доступний у будь-якій точці виклику (логери, сервіси, обробник помилок) без зміни сигнатур функцій.
