## 2. Одна команда

```bash
make test            # або npm run test:all — те саме без make (Windows)
make mutation        # або npm run test:mutation — Stryker, звіт reports/mutation/mutation.html
```

`make test` → [`scripts/test-all.js`](scripts/test-all.js):

1. `docker compose up -d --wait postgres` — піднімає БД і чекає healthcheck;
2. unit + API з порогами покриття (БД не потрібна);
3. integration — `globalSetup` створює `taskflow_test` і застосовує міграції;
4. E2E — `globalSetup` **видаляє і створює** `taskflow_e2e_test`, запускає справжній сервіс на
   вільному порту (сервіс сам мігрує порожню БД), чекає `/health`; `globalTeardown` вбиває процес.

Кожна стадія виконується навіть якщо попередня впала; в кінці — зведення і ненульовий exit code.
Перевірено «з нуля»: `docker compose stop` → `npm run test:all` → контейнер стартує → 4/4 PASS.
Тестові БД мають guard: назва без `test` → тести відмовляються запускатись (вони роблять
`TRUNCATE`/`DROP`).

## 6. Аудит: топ-3 місця, де «зелені» тести не ловили реальні баги

Усі три — **реальні баги в коді з `main`**, при яких увесь набір тестів був зелений.

### 1. Одна задача — два різні `createdAt` (POST vs GET) — `6fe5fb8`

- **Баг**: `POST /projects` віддавав задачі через драйвер `pg` (`"…06.478Z"`), а
  `GET /projects[/:id]` — через `json_agg`, де PostgreSQL сам форматує `timestamptz`
  (`"…06.478225+00:00"`). Клієнт, що порівнює/кешує дані, бачив дві різні задачі.
- **Чому тести мовчали**: API-тести працюють на in-memory прототипі, де всі дати — ISO-рядки,
  тобто цей клас багів там _структурно неможливий_. Інтеграційні тести перевіряли кількість рядків
  і статуси, а не форму відповіді.
- **Підсилення**: інтеграційний тест порівнює **повні тіла** `POST` і `GET` (`toEqual`) + формат
  дати регуляркою. Спершу написав тест — він впав з тим самим diff, потім виправив SQL
  (`to_char(... AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')`). E2E-крок 4 перевіряє те
  саме через справжній процес.

### 2. Дірки в контракті помилок — `aa2ea01`

- **Баги**: (а) `POST /tasks` або `PATCH /tasks/:id/status` без JSON-тіла → **500**
  `Cannot destructure property 'title' of 'req.body'` (у `projectsController` захист `?? {}` був,
  у `tasksController` — ні); (б) зламаний JSON → `400` з `code: "INTERNAL_SERVER_ERROR"`;
  (в) невідомий маршрут → HTML-сторінка Express замість JSON; (г) будь-яка 500 віддавала клієнту
  сирий текст помилки (TypeError, повідомлення драйвера).
- **Чому тести мовчали**: усі тести слали «правильні» запити з JSON; шлях «невідома помилка → 500»
  не мав жодного тесту (Stryker: `NoCoverage` на fallback-рядках `errorHandler`).
- **Підсилення**: API-тести на запити без тіла / зламаний JSON / невідомий маршрут; unit-тести
  `errorHandler` на кожну гілку (AppError, невідома помилка, драйверна помилка, body-parser 400/413,
  `expose`, межа 499/500, рівень лога); E2E — контракт помилок через справжній HTTP.

### 3. Перевірка статус-коду замість даних і меж

- **Баги, які пропускав старий набір** (перевірено: закладав баг вручну і ганяв `app.test.js` з
  `main` проти нового unit + API набору):

  | Закладений баг                                   | Старий `app.test.js` (36) | Нові unit + API (230) |
  | ------------------------------------------------ | ------------------------- | --------------------- |
  | `userId: 0` приймається (`value >= 0`)           | 36 passed                 | 4 failed              |
  | `POST /tasks` зберігає задачу без назви          | 36 passed                 | 3 failed              |
  | `DELETE /projects/:id` не видаляє задачі проєкту | 36 passed                 | 1 failed              |
  | назва рівно 255 символів відхиляється            | 36 passed                 | 3 failed              |
  | `/projects/01` приймається (regex без `^`)       | 36 passed                 | 8 failed              |

- **Чому тести мовчали**: `POST /tasks` перевіряв лише `status: 'TODO'` (а це дефолт репозиторію);
  тест каскадного видалення перевіряв лише `404` на проєкт, а не задачі; межі перевірялись
  «далеко» (`99999999999`, 256 символів), а не на самій межі.
- **Підсилення** (`3ed7956`, `4380839`): API-тести перевіряють дані (`title`, `projectId`, що
  задачі видаленого проєкту зникли, а чужі — ні; що після 400 не лишилось «сиріт»-задач);
  unit-тести на межі з обох боків; тест машини станів на **всі 9 пар** `(from, to)`, щоб додавання
  або зникнення будь-якого переходу ламало тест.

## 7. Аналіз ефективності тестів

- **Покриття ≠ ефективність.** На baseline `validation.js` мав 100% branch coverage і 81% mutation
  score; `tasksService` — 83% гілок і 55% mutation score. Покриття показує, що код _виконано_;
  mutation score — що результат _перевірено_. Тому пороги стоять на обох.
- **Рівні не дублюють один одного.** Баг №1 неможливо побачити на in-memory рівні, лише на
  integration/E2E. Fail-fast старту без БД, міграцію порожньої БД, exit code процесу і реальний
  лог-потік бачить лише E2E (`startup.e2e.test.js`, `observability`). Межі валідації дешевше й
  повніше перевіряти unit-тестами (57 випадків за ~0,1 с), ніж HTTP-запитами.
- **Слабкий тест, що лишився свідомо**: mock-тест N+1 у `postgresRepositories.test.js` перевіряє
  _текст_ SQL (`toContain('json_agg')`), тож пройде і з неправильним SQL. Справжню перевірку
  «рівно 1 запит + правильні дані» робить інтеграційний тест; mock-тест лишився як швидкий
  сигнал у pre-push.
- **Обмеження**: Stryker мутує бізнес-логіку й шлях помилок, але не SQL-репозиторії (кожен мутант
  потребував би БД; їх стереже integration з 100% рядків). Конкурентність перевірено одним
  сценарієм (5 паралельних запитів з одним Idempotency-Key); навантажувальних тестів немає.
